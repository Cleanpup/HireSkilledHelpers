A. High-level recommendation
Use a mixed architecture: worker appears as a normal in-world NPC actor, 
but behavior is chosen by a host-authoritative runtime controller (not schedule-only logic). 
This gives you the best balance of shippable gameplay, mod compatibility, and a clean runway toward traditional AI
 without a full rewrite.

1. Hybrid NPC shell + custom runtime brain (recommended)
- Concept: Reuse vanilla NPC/world integration, but runtime controller selects goals, destinations, and actions continuously.
- Feasibility: High.
- Maintainability: High if you separate decision layer from movement/persistence.
- Compatibility: High-medium (mostly vanilla-compatible, minimal targeted hooks).
- Pathfinding: Medium; leverage vanilla path controllers, add custom replanning/recovery.
- AI growth: High; easy progression from FSM to utility-based behavior.

C. Engine/system constraints from SMAPI + Stardew 1.6
1. Update loop and lifecycle boundaries
- Runtime decisions should run on game-loop events, with strict world-ready checks.
- Relevant hooks: IGameLoopEvents.cs, IGameLoopEvents.cs, Context.cs.

2. Pathfinding and collision pain points
- Dynamic destinations are viable, but route failure, tile occupancy changes, and blocked chokepoints must be handled explicitly.
- Core references: PathFindController.cs, PathFindController.cs, GameLocation.cs, GameLocation.cs.

3. Schedule interruption and event interference
- Vanilla NPC systems prioritize certain controllers/schedule states; runtime worker logic must pause/resume cleanly around events/festivals and forced movement.
- Relevant anchor: NPC.cs, NPC.cs.

4. Map changes and custom locations
- Dynamic map edits, missing warps, and custom location availability can invalidate routes mid-task.
- Use defensive destination validation before commit/repath.

5. Multiplayer authority and syncing
- Host should own all AI decisions and state mutation; clients should render mirrored results and send requests only.
- Relevant systems: Multiplayer.cs, Multiplayer.cs, IMultiplayerEvents.cs, IMultiplayerHelper.cs.

6. Persistence/save data
- Persist worker brain/task progress in mod save data, rehydrate at load/day start, clear on return-to-title.
- Existing repo pattern to reuse: ModEntry.cs, ModEntry.cs.

D. Best architecture direction
Treat this as mostly NPC presentation plus custom runtime logic, not a fully custom entity.
1. Worker body: vanilla NPC-compatible actor in location character lists.
2. Worker brain: custom decision service that picks next task/destination from live world/business state.
3. Worker execution: movement/path controller layer with retries, reroutes, and interruption handling.
4. Worker data: mod-owned persistent state (task token, role state, cooldowns, last valid destination).
5. Worker networking: host-authoritative decisions, client mirror-only.

This mixed direction is the strongest fit for your three goals:
- Shippable soon
- Good AI learning substrate
- Minimal rewrite risk later

E. AI model recommendation (FSM vs behavior tree vs utility AI)
Best fit now: FSM with utility scoring inside states.
1. FSM for top-level reliability
- Clear, debuggable states like OffDuty, TravelToTask, PerformTask, Recover, Idle.
- Great for first shippable versions and edge-case control.

2. Utility scoring for dynamic runtime choices
- Inside PerformTask/SelectTask phases, score candidate jobs from world state (distance, urgency, business demand, fatigue, time window).
- This gives runtime-derived behavior without full planner complexity.

3. Behavior tree later, only if needed
- Adopt BT when behavior breadth and interruption combinatorics grow large.
- Not ideal as a first model here because you still need strong world-specific recovery and host-sync discipline first.

In short:
- Phase 1-2: FSM
- Phase 2-3: FSM + utility (recommended long-term baseline)
- Later only: BT for large behavior libraries

W. Player-farm fishing — implemented for testing, not yet released
Adds Your farm as a Fisher destination regardless of SVE presence. This implements backlog item 3 through the real farm map/data instead of a whitelist of farm types. A bounded walking search from the worker's current Farm position or the farmhouse entry finds reachable dry banks, preserves collision/occupancy/warp/touch-action guards, and allows only continuous short casts into fishable water. Constructed Fish Ponds are excluded. Banks with configured normal fish pools are preferred over trash-only ponds; if only trash water exists, it remains castable without invented fish. If no safe spot exists, the order waits without new casts/stamina spending, reports No accessible fishing spot on this farm in the business-menu footer, mirrors the state to farmhands and retries at a throttled interval. Clearing/reassigning can recover without altering the map.

The SVE data adapter is generalized as WorkerLocationFishing. Farms use their own GetData results, including vanilla per-farm fish areas, bounded LOCATION_FISH inheritance, CanBeInherited flags, both nested/parent bite checks and FarmFishLocationOverride chances. This supports ordinary data-driven custom farms without requiring SVE. Other scripted getFish overrides and arbitrary item-query handlers remain separate compatibility work. A saved IsLiveDataCatch marker preserves validated custom-farm fish through reloads/missing definitions without permitting unvalidated new rewards. Prior SVE behavior and its checks remain covered.

Validation: build clean, original fishing and SVE fixtures pass, topology checks cover no water/disconnected/bridged/blocked/reopened shores and map bounds. Y. Independent Miner production — implemented for testing, not yet released
Miners now have an Independent mining order in addition to their three physical jobs. A separate Expedition destination selects Mines, Skull Cavern or Volcano with the same unlock gates, safe permanent-entrance placement, active-hour timing (6:00–22:00), maximum 16 runs/day, return-home handling and worker-specific chest/shipping delivery as Fighter Explore Area. This is a stationary simulation, no dungeon generation or physical rock destruction, with no tool stamina charge just like Fighter exploration. Each completed batch awards 5 Mining XP and no player/Combat XP. Physical Mining area remains independent of Expedition selection. Console: workers assign <id> independentmine; workers expedition-area <id> <mines|skull|volcano> (explore-area alias retained).

The shared saved expedition queue tags mining rewards explicitly; old untagged rewards remain governed by the Fighter allowlist. Finished mining batches survive reload, area/role changes and dismissal delivery, with one completion/XP award before retryable storage. Cancellation clears unfinished time but never finished rewards or the daily run counter. Paused menus/events observe the expedition clock without accruing time. Host-only assignment and production remain enforced.

WorkerMiningLootCatalog uses the host's deepest recorded mine floor and team.sharedDailyLuck (clamped -0.1 to +0.1, no player charm/equipment). Mines cap ore evaluation at 119, with copper/iron/gold bands at 20/40/60/80; floor 120 adds a very rare shard. Skull uses recorded depth minus120: iridium ore share 10/20/30/40 percent at introductory/25/50/100-floor bands. Volcano is access-gated with a fixed copper/iron/gold/cinder/iridium pool, since ordinary deepestMineLevel does not record Volcano progress. Each hour rolls one 3–5-unit core resource batch plus a luck-sensitive extra unit and independent coal/gem/geode/rare-shard bonuses. No stone, bars, monster materials, quest items, artifacts or radioactive ore. All probabilities are explicit worker balance, not native per-rock chances.

Subagent analysis and 7.2 million C# simulated hours verified the catalog. Expected total units per hour are 5.02/5.35/5.68 at bad/neutral/good luck, excluding at most 0.0012 rare shards/hour.
